01 / BEHAVIOR

A collaborator, not a second parent.

This proposal adds one narrow relationship: a parent may spawn a named Sidekick during its session, delegate bounded work, and address that same handle while it remains live. It is not durable memory, a new scheduler, or an independent authority.

Proposed behavior — not implemented runtime behavior

A Sidekick owns private working context retained across its delegated tasks in the parent’s current session. The parent receives compact summaries with traceable evidence references, not raw command logs. The parent alone synthesizes user-facing answers and makes decisions.

Retain

Working set

Keep delegated prompts, tool results, intermediate findings, and task history while the Sidekick runs.

Return

Small evidence

Return conclusions, uncertainty, and references to retained artifacts or tool calls—never an unbounded transcript.

Do not promise

Cross-session memory

At parent session end, Sidekicks stop. This proposal makes no restart or cross-session persistence claim.

02 / LIFECYCLE

Alive only alongside its parent.

SpawnParent names role, task boundary, and delegated tools.
IdleHandle is addressable; private context remains available.
BusyOne delegated run is active; the handle reports status.
Idle againFollow-up delegates reuse its retained context.
StopRelease live context and handle; a read-only display transcript may remain.
Session endStop every remaining Sidekick. No survival promise.

What persists

  • The running Sidekick’s private context across parent tasks.
  • A durable handle while its state is idle or busy.
  • Its bounded delegated tool grant and parent approval policy.

What does not

  • Authority to make parent decisions or respond as the parent.
  • Permission to acquire tools, approvals, or write access on its own.
  • Any live execution context or reusable handle after explicit stop, failure cleanup, or parent session end. A read-only display transcript may remain where the UI retains it.
03 / AUTHORITY

Configured tools are inherited, never an escape hatch.

V1 gives a Sidekick the configured child tool factory and applies the parent’s existing inherited policy and approval path. It creates no new grant and has no per-Sidekick allowlist.

Tool ownershipOwns the configured child tools and inherited enforcement.May invoke only those configured tools through the same dispatch path.

Concurrency rule. A Sidekick must not rely on its per-agent dispatcher for global exclusion: current evidence shows each child has its own dispatcher. V1 adds no cross-agent lock, so the parent must avoid or serialize conflicting mutations.

08 / API

Small shipped surface.

Sidekicks reuse the existing subagent protocol and SDK session-owned Subagents handle. There is no second scheduler, permission system, global lock, or renderer.

Model tool protocolbackground by default
// Returns immediately: { spawnId: 19, status: "running", persistent: true }
{ "task": "Trace the fixture failure.", "persistent": true }

// Same stable handle and retained Context; also returns immediately.
{ "action": "task", "spawnId": 19, "task": "Check other fixtures." }

// Explicit old-style awaited operation.
{ "action": "task", "spawnId": 19, "task": "Summarize.", "background": false }
Rust SDKactual API
let ack = session.subagents().unwrap()
    .start_sidekick(SubagentRequest::new("Trace the fixture failure."))?;
let follow = session.subagents().unwrap()
    .sidekick_task(ack.spawn_id, "Check other fixtures.")?;
// Await explicitly when required:
let report = session.subagents().unwrap()
    .sidekick_task_foreground(ack.spawn_id, "Summarize.", None, None).await?;
session.subagents().unwrap().stop_sidekick(ack.spawn_id)?;
Stable identity
Every turn uses the same spawnId and retained actual child Context.
Completion
Every background turn, including failure, enters the existing completion inbox and host notification channel; repeated turns are not deduplicated by spawnId.
V1 limits
Session-scoped only. Configured child tools and inherited policies/approvals apply. No per-Sidekick grants, cross-session restoration, autonomous scheduler, or cross-agent global write lock.
09 / FAILURE

Stopping must mean stopped.

Failure & cancellation

A background initial or follow-up failure is delivered through the normal completion lifecycle and leaves the disclosed handle idle and reusable. An explicit foreground initial failure removes its undisclosed handle. Failures do not silently become a parent answer. Parent cancellation cascades to Sidekick model/tool work. A Sidekick cancellation affects only that Sidekick unless the parent chooses otherwise.

Explicit stop

stop() prevents new delegations, requests cancellation for active work, awaits normal cleanup where possible, then removes the handle and live private context. Cleanup is idempotent. The browser may retain a read-only display transcript, but it cannot restore the handle or make follow-up possible; a later task requires a new spawn.

Background-default v1. Creation and each action=task follow-up return the stable spawnId immediately with running or queued; completion is delivered through the existing inbox/event path and the handle returns to idle. Set background=false to await a task explicitly. Reports are prompt-guided compact answers, not an enforced schema.
Busy handle rule. A Sidekick processes one delegated task at a time. A second request while the handle is queued or running is rejected deterministically to keep task and context ordering clear.
10 / ACCEPTANCE

What proves the proposal works.

  1. A parent can spawn a Sidekick using configured child tools and inherited policy/approval enforcement, without minting new grants.
  2. A Sidekick retains delegated context across at least one follow-up while its parent session remains active.
  3. Parent context receives compact summaries and evidence references, not raw Sidekick tool logs by default.
  4. A Sidekick cannot invoke ungranted tools, alter approval policy, or self-approve an action.
  5. Mutating work follows the existing keyed/serial concurrency rules across parent and Sidekick calls.
  6. Status and events expose queued, busy, idle, failed-task, stopped, and session-ended outcomes without implying cross-session durability.
  7. Parent cancellation and explicit stop reach in-flight Sidekick work; stop is idempotent, removes future handle access and live context, while any retained browser transcript is read-only.
  8. Session end stops all Sidekicks and releases their private contexts.
  9. The parent remains the sole owner of decisions and user-facing synthesis.
V1 boundary

Stop at persistent-in-session private context, configured child tools, lifecycle control, and compact reports. Do not add cross-session restoration, autonomous scheduling, Sidekick-to-Sidekick messaging, new permissions, or a separate persistence service.
