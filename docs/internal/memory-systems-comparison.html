Memory is not one thing.

Four products use the word for four different contracts: explicit preferences, live personalization, background learning, and resumable conversation state. This report separates them and documents the resulting OrcaCode memory extension.

Four contracts

The most important design choice is not the database. It is what “remember” means, who authorizes the write, and when stored knowledge gains influence over a future model turn.

fx / explicit register

User-controlled preferences

A deliberately small global JSON list. The model may save, list, or clear only when the user explicitly asks. Nothing is inferred, ranked, or automatically injected.

Brain Dump / live profile

Online personalization

Structured per-user records are automatically retrieved on every normal chat and may be inferred during that chat. Relevance and confidence directly shape the next prompt.

Codex / learned handbook

Background operational learning

Past rollouts are asynchronously extracted, selected, and consolidated into a progressive-disclosure file workspace that future agents are instructed to search.

Pi / durable continuity

Session state, not semantic memory

Append-only branching JSONL, compaction summaries, and context files preserve continuity. A semantic memory system can be built as an extension, but is not built in.

How each works

Each implementation is useful because it optimizes a different point in the trust, complexity, and recall-quality space.

01 / fx

One tool, one file, explicit intent

The built-in tool accepts save, list, or clear. It reads an array of strings, deduplicates by exact equality, and atomically rewrites the JSON file. The product description forbids task notes, secrets, project facts, temporary context, and unsolicited persistence.

  • Excellent auditability and minimal prompt influence.
  • No automatic relevance, project scoping, record-level deletion, or provenance.
  • Malformed or oversized stores fail closed instead of being overwritten.
02 / Brain Dump

Structured records in the live chat loop

Every normal client request enables memory. The server injects high-confidence core facts and lexically relevant records into the system prompt, then gives the model tools to query and mutate the store. Automatic inference is capped at two saves per request and performs exact and topic-level duplicate checks.

  • Fast personalization with explicit confidence, access, and staleness fields.
  • Relevance is full-text plus hand-built lexical clusters, not embeddings.
  • The server service role bypasses RLS, so application-level userId filters are the real tenant boundary.
03 / OpenAI Codex

Two-phase asynchronous consolidation

On eligible root-session startup, phase one claims recent idle rollouts, filters them, asks a model for raw memory and a compact summary, redacts generated secrets, and writes stage-one records. Phase two selects a bounded usage-ranked set, synchronizes files, and runs a sandboxed consolidation agent against a git-style workspace diff.

  • memory_summary.md is prompt-loaded but bounded; richer artifacts are searched only when relevant.
  • MEMORY.md, rollout summaries, and reusable skills form a progressive-disclosure hierarchy.
  • Global consolidation improves repeated work but introduces latency, model cost, and cross-project contamination risk.
04 / Pi

A durable session substrate

Pi appends typed entries to versioned JSONL. id/parentId form an in-file tree, so users can branch without discarding history. When context approaches its window, Pi summarizes older messages, appends a compaction entry, and rebuilds model context from the summary plus recent messages.

  • Global and ancestor-directory AGENTS.md/CLAUDE.md files provide durable authored guidance.
  • Extension custom entries survive reload but stay out of model context unless deliberately injected.
  • The extension lifecycle can support semantic memory without forcing one storage or retrieval policy into core.

Codex pipeline

Codex separates expensive learning from the interactive turn. Brain Dump performs retrieval and possible inference inside the chat request; this pipeline runs later and consolidates globally.

Eligible rollout Interactive root session, old enough, idle, non-ephemeral, memory-enabled.
Phase one Filter response items, model-extract raw memory and summary, redact generated secrets.
SQLite state Lease jobs, store stage-one output, retry with backoff, track usage and selection.
Phase two Select bounded inputs, sync artifacts, run a no-network consolidation sub-agent.
Future turn Inject bounded summary, then grep the registry and evidence only when the query needs it.

Failure modes

Memory becomes durable prompt influence. Failures are therefore more serious than ordinary cache misses: the system can repeatedly act on stale, cross-scoped, or incorrectly inferred guidance.

Brain Dump / consent

Enabled is not the same as opted in

Both normal chat clients set memoryEnabled = true. The server describes this as an opted-in state, but no matching user setting was found.

Brain Dump / consistency

Tool mutations bypass cache invalidation

REST update and delete invalidate the five-minute core-memory cache. Chat save, update, merge, and delete tools mutate the store directly, so stale core facts may remain prompt-visible until expiry.

Brain Dump / concurrency

Limits and deduplication are not atomic

Per-request reservations prevent more than two auto-saves inside one request, but concurrent requests can both pass count and duplicate checks before inserting.

Codex / scope

Global summary crosses repository boundaries

Consolidation organizes knowledge by cwd, but the read path loads the global memory_summary.md wholesale, subject to a token cap rather than cwd filtering.

Codex / complexity

Learning is eventually consistent

Eligibility windows, idle thresholds, stage claims, model extraction, selection, and consolidation mean a useful lesson is not immediately available to the next session.

Pi + fx / recall

Safety trades against discovery

Explicit lists and session-local continuity minimize unintended influence, but durable facts are easy to miss unless the user or model remembers to retrieve or author them.

OrcaCode direction

The kernel states that model-visible context is not durable memory and that memory belongs in an extension or host. The implementation keeps that boundary and composes with existing JSONL sessions instead of turning them into a fact database.

Recommended synthesis

Use one embedded SQLite FTS5 database as the only source of truth.

MemoryExtension, memory_search, and memory_manage share ~/.config/orcacode/memory.sqlite3. SQLite runs in the OrcaCode process and owns transactions, locking, scope filtering, and text ranking.

  • Never put persistence, ranking, or consent policy in harness-core.
  • Keep session resume, compaction, and durable semantic memory as separate stores and lifecycles.
  • No daemon, subprocess, generated manifest, Markdown mirror, or duplicated source ledger.
  • Do not grant remembered text the same authority as developer policy; add it only as clearly delimited user-owned context on a transient request clone.

Workspace identity contract

Persist identity and provenance with every memory.

Resolve workspace identity from the trusted runtime root. The is_global boolean plus nullable workspace_id form a checked database invariant; never accept a model-supplied workspace ID.

id
Opaque mem_ identifier backed by 128 random bits. SQLite's integer rowid stays private to indexing and FTS joins.
is_global
Boolean scope flag. true applies across workspaces and is reserved for information that clearly applies everywhere.
workspace_id
Opaque stable identifier derived from the canonical runtime workspace root. Required when is_global = false.
workspace_root
Canonical runtime root retained as readable workspace metadata.
source_call_id
The exact memory-management tool call that created the record.
1

One authoritative database

Ship save, search, list, update, and forget behind an extension.

  • memories holds an opaque public ID, content, kind, scope, workspace metadata, source call, and timestamps.
  • memories_fts is an external-content FTS5 table synchronized by database triggers.
  • A schema check enforces global XOR workspace scope.
  • SQLite WAL provides local transactions and concurrent-process locking.
2

Scoped FTS retrieval

Run one FTS5 query where is_global = true OR workspace_id = current_workspace_id, order by FTS5 rank, and add a character-capped fragment to a transient user-authority request clone.

  • Use deterministic FTS5 before adding semantic machinery.
  • Read at most eight matching records by default.
  • Return provenance with every recalled item.
  • Let the model propose stable, directly stated, future-useful memories; reject low-value, duplicate, secret, transient, or inferred content.

Measured benchmark: across 100 Criterion samples over 50,000 records, exact raw SQL measured 93.35 µs, MemoryStore::search 95.53 µs, and safe transient MemoryExtension::prepare_context 95.98 µs. A worst-case broad query matching every row measured 34.38 ms end to end. With opaque public IDs, a scoped raw DELETE measured 65.46 µs and the complete memory_manage(forget) call with no approval layer measured 64.25 µs; their overlapping intervals put tool overhead below measurement noise. Reproduce with cargo bench -p orca-harness-extensions --bench memory.

OrcaCode sequence

The implemented read and model-selected write turn. A user request or stable future-useful information can trigger a proposed mutation. The host supplies trusted workspace identity, and normal approval remains the user's final decision.

Read boundaryOnly global and current-workspace records can be returned or enter model context; FTS5 corpus statistics remain database-wide.

Write boundaryThe model requests a scope, the host supplies the effective workspace ID, and SQLite enforces the global XOR workspace invariant.

Authority boundaryRemembered text is delimited user-authority context on a transient request clone, not developer policy and not permission to act.
