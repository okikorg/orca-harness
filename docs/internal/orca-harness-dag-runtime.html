Parent submits a graph / harness runs it

Three hash maps.One entry method.

A workflow is a graph the parent composes per run and submits as a tool argument. The harness validates it, admits it, and advances it from the completion path subagent.rs already drives. No embedded runtime, no sidecar process, no second channel, no config files — and one new field on SubagentSpawn carries the whole context-isolation story.

DECISION

What is being proposed

Multi-agent work today is a star: the parent spawns detached subagents and every result returns to the parent's context. That makes any multi-stage job expensive — each intermediate artifact is read and re-written by the orchestrator — and it makes the shape of the work implicit in a conversation rather than explicit in a structure.

A DAG runtime replaces the star with a graph the parent writes once. Stages are ordinary detached subagents; what changes is where their results land. The parent's context grows by exactly two messages per run: the submission and the terminal outcome.

ENGINE

Three maps and one method

An adjacency map alone is not enough, and the reason is worth being concrete about. Given A → {B, C} and B → D, C → D, walking the adjacency list on each completion fires D twice — once when B lands, once when C does. Fan-in is the only thing separating a DAG from a tree, so the counter is not optional.

Adjacency answers "who is downstream". The counter answers "is it time yet". Both are HashMaps; neither needs a graph library.

crates/harness-dag/src/engine.rsno spawn ids here — those are the overlay's
pub struct Dag {
    edges:     HashMap<StageId, Vec<StageId>>,  // who is downstream
    pending:   HashMap<StageId, usize>,         // unsatisfied parents
    output:    HashMap<StageId, String>,        // every answer so far
    in_flight: HashSet<StageId>,                // emitted, not yet completed
    state:     RunState,                          // Running | Cancelled | Done
}

impl Dag {
    /// The only entry point. Called from the stage branch of `publish`,
    /// synchronously, and returns immediately. Nothing waits on anything.
    pub fn complete(&mut self, stage: &StageId,
                    result: Result<String, String>) -> Advance {
        self.in_flight.remove(stage);
        let answer = match result {
            Ok(answer) => answer,
            // A failed or cancelled stage fails the run: its downstream
            // can never be satisfied, so pending would never reach zero.
            Err(error) => return self.fail(stage, error),
        };
        self.output.insert(stage.clone(), answer);
        self.expand_if_map(stage);        // may insert edges and counters
        let mut ready = Vec::new();
        for next in self.edges[stage].clone() {
            let n = self.pending.get_mut(&next).unwrap();
            *n -= 1;
            if *n == 0 { ready.push(next); }
        }
        self.emit(ready)   // Spawn(..) | Done(..) | Stalled(..)
    }
}
The load-bearing invariant While anything is in flight a completion is always coming. So in_flight empty with pending non-empty is Stalled, never a wait — and emit asserts it on every advance rather than letting a run hang.

ISOLATION

One field on SubagentSpawn does the work

SubagentSpawn (subagent.rs:95) is already threaded through every layer a completion passes: it is stored on the job, moved into Completion, and handed to the notifier verbatim. Adding run: Option<RunId> puts the routing decision exactly where it is needed, with no lookup table and no second registry.

pub(crate) fn publish(&self, notification: SubagentNotification, ui: .., worker: ..) {
    let _ = ui.send(UiMsg::SubagentCompleted { .. });  // unchanged: UI always settles
    if let Some(run) = notification.spawn.run {
        if !self.manager.is_current(notification.generation) { return; }  // stale
        self.runs.advance(run, notification);   // lock, complete(), unlock, then act
        return;
    }
    if self.push(notification) && self.request_wakeup() {
        let _ = worker.send(WorkerCmd::BackgroundSubagentsReady);
    }
}

// crates/tools/src/subagent/background/manager.rs:236 — the capacity change
if let Some(capacity) = state.completion_capacity {
    if spawn.run.is_none() {            // stages are never delivered, never reserve

Recommended, not settled — a run-level spawn push requires a notification with a real spawn and a current generation, and a run has neither. The clean answer is for the run action to admit one run-level SubagentSpawn at submit, with run: None and the graph summary as its task, and no agent behind it. That single spawn does four jobs: it gives the terminal notification a generation to be checked against, it reserves exactly the one completion slot the parent will consume, it gives the TUI a row for the run, and — because stages then carry parent_id = Some(run) — it keeps them out of the inline transcript entirely. The caveat: admit hands a spawn a Slot if it heads the queue with capacity free, and a run-level spawn holding a slot would steal one unit of concurrency for its whole lifetime. It needs a no-slot admission — reserve delivery, skip try_start. Small, but it is a manager change, which is why this is flagged rather than assumed.
05
THE TOOL

What the parent actually sees

One tool, shaped like the subagent tool it sits beside: an action enum with a oneOf discriminating required fields, exactly as subagent_parameters builds it at background/protocol.rs:8. Reusing that shape matters more than it sounds — the parent already knows how to drive a detached tool that refuses to be polled.

There is no workflow file. The parent composes a graph for the job in front of it and submits it as the tool's argument. Determinism is not lost by this: the graph is fixed and checked before any stage model runs, so nothing downstream depends on a model's turn-by-turn choices. Validation stops being a file lint and becomes ordinary tool-input validation, which is a better place for it.

Map expansion, the one delicate part

Everything else is bookkeeping. This is where the design can quietly break: an answer is a free-form string (background.rs:70) and map has to turn it into N stages.

Declare the shape

A stage feeding a map must carry schema; the engine parses answer before expanding.

Re-ask once, then fail

A parse failure re-spawns the source with the parser error appended. A second failure fails the run rather than guessing.

Cap the fan-out

Reject a 400-item expansion at expansion time, not after 400 admissions.

Zero is not silent

An empty list is legal but a common failure signature; it marks the run degraded and says so in the terminal summary.

Honest qualification to "zero parent tokens" That holds for stage results, which is where the volume is. Emitting the graph costs the parent a few hundred tokens, once. A twenty-way map expansion still costs nothing, because the parent wrote one stage and the harness made twenty.

CRATE

A DAG crate that knows nothing about agents

The engine is its own crate, named orca-harness-dag to match the workspace convention. Its dependency list is the proof the boundary is real: serde and serde_json, nothing else. No tokio, no async-trait, no orca-harness-core.

Be clear about the payoff, though: nothing outside this repo will depend on it. The win is not reuse, it is that the scheduler becomes a deterministic, synchronous state machine testable with plain #[test] — no runtime, no ScriptedModel, no timing. Every fan-in, expansion, stall and cancellation case is a unit test that runs in microseconds.

pub enum Advance {
    /// Launch these. The host decides how.
    Spawn(Vec<Stage>),
    /// The graph drained. Deliver this.
    Done(RunOutcome),
    /// Invariant broken: nothing in flight,

    Stalled(StallReason),
}

fn apply(&self, run: &Run, advance: Advance) {
    match advance {
        Advance::Spawn(stages) => for stage in stages {
            let req = SpawnRequest {
                task: stage.prompt,
                model: stage.model,
                call_id: run.call_id.clone(), // the `workflow run` call
                run: Some(run.id),
                ..Default::default()
            };
            match self.subagent.spawn(req) {
                Ok(ack) => run.live.insert(ack.spawn_id, stage.id),
                // only a route change mid-run can land here
                Err(e) => self.advance(run.id, &stage.id, Err(e)),
            }
        },
        Advance::Done(outcome) => self.complete_run_spawn(run, outcome),
        Advance::Stalled(why) => self.fail_run(run, why),
    }
}
// `live: HashMap<u64, StageId>` lives on Run, here — not in the crate.
The seam, named The DAG crate emits intentions and consumes facts. It never learns that a stage is a language model, that spawning can queue, or that a result travels through a notifier. Everything harness-shaped — admission, slots, cancellation tokens, the completion path — lives in the overlay, which is roughly one file.

CANCELLATION

Three stops, and they are not the same

There is no run-level cancellation token, and there does not need to be one. admit owns token creation — it hands each job a state.cancellation.child_token() off one manager-wide root (manager.rs:243) and takes no parent argument, so a per-run token would mean changing its signature. Iterating the run's live spawns does the same job with no manager change at all.

StopMechanismWhat the engine must do
One stage
manager.cancel(spawn_id)		 Cancels that job's token only. Everything else keeps running. Fail the run. The stage's downstream can never be satisfied, so marking it done-with-empty-output leaves pending permanently above zero — the stall, arriving through the cancel path.
One run
the new case		 Cancel each live spawn, then flag the Dag. Stages not yet spawned exist only in the ready set, which the flag stops draining. Absorb what arrives. A cancelled Dag takes completions without advancing counters and emits one terminal outcome.
Everything
cancel_all		 Cancels the root, bumps generation, clears jobs and queue. Leaves running alone so slots free as workers actually exit. Drop every live Dag. Stale completions never arrive, so a run left in the map hangs forever.
cancelling one runno manager change, no new token
fn cancel_run(&self, run: RunId) {
    let live = {
        let mut runs = self.runs.lock().unwrap();
        let dag = runs.get_mut(&run)?;
        dag.cancel();                  // stops draining ready, absorbs arrivals
        dag.live_spawns()              // stages currently admitted or running
    };
    for spawn_id in live {
        self.manager.cancel(spawn_id); // manager.rs:342, per-job token
    }
}
Why the flag is sufficient Cancelled stages still report. Completion::drop is a Drop impl, so it fires on the interrupted path too — "subagent execution interrupted" for a running stage, or "subagent cancelled before execution" for a queued one, since acquire selects on the token, dequeues, and returns None (manager.rs:316). Every cancelled stage produces exactly one completion, so the engine's accounting stays closed whichever way a run ends.

CONCURRENCY

Who owns &mut Dag

CompletionInbox::publish takes &self and is called from arbitrary tokio tasks, since Completion::drop runs wherever the worker finished. So runs live beside the inbox in a Mutex<HashMap<RunId, Dag>> — a plain std::sync::Mutex, not tokio's.

That is safe only because the DAG crate is synchronous and IO-free: complete() is map arithmetic with no .await in it, so the lock is held for microseconds and can never be held across a yield point. This is the concrete payoff of the crate having no tokio dependency, beyond testability.

lock, advance, release, then act
let advance = {
    let mut runs = self.runs.lock().unwrap();
    runs.get_mut(&run)?.complete(&stage, answer)
};
self.apply(run, advance);   // spawns happen with no run lock held
Never hold the run lock while spawning SubagentTool::spawn takes the manager's own state mutex during admission, so calling it under the run lock creates two lock orders that can invert against an arriving completion. Advance under the lock, drop it, then act on the returned Advance.

Re-entrancy is safe, but by construction rather than by luck: detach_subagent hands the work to tokio::spawn (background.rs:96), so a stage can never complete on the same stack that spawned it and call back into publish. This holds only because stages always detach — one more reason the engine never touches the foreground path at subagent.rs:584.

What scales for free nested_subagent_lines selects spawns where parent_id.is_none() && call_id == call_id, then takes .max() (transcript.rs:233). Stages carry parent_id = Some(run), so they are filtered out entirely; only the run-level spawn matches, and it has no tools of its own. Four things that break at DAG scale

ProblemDetail and fix
The browser draws the spawn tree, not the dependency graph build_agent_tree_rows groups by parent_id (list.rs:160). Every stage's parent is the run, so all 54 are siblings at depth 1 — a flat list wearing branch glyphs, with the graph shape invisible. That shape is the only reason to open this view for a large DAG. Cheap partial fix: on map expansion, set each expanded stage's parent_id to the source stage's spawn id rather than the run's. Map chains are where the fan lives, so dimensions → 12 reviews → 40 verifies renders as a real three-level tree for free. needs edges still will not show, but those are few.
History eviction deletes a live run's stages retain_agent_history keeps 100 completed transcripts and evicts oldest-first (subagent_history.rs:103). Two 54-stage runs exceed that in one session. Evicting completed stages of a run still being read makes rows vanish; worse, if a finished run's own row is evicted while any stage survives, the orphan fallback at list.rs:188 promotes every remaining stage to a root and the list silently reshapes. Retention has to become run-aware: evict whole runs, not individual transcripts.
Queued stages flood the default tab AgentTab::Running admits is_active(), which is Queued or Running (subagents.rs:257). A 40-way map at background limit 4 shows 4 running and 36 queued, all sharing the same mark and differing only in colour and · queued · 0s. Either collapse consecutive queued siblings into one … 36 queued row, or give queued its own glyph.
Per-frame cost is O(total transcripts) agent_table caches only when every row is terminal (list.rs:47), so during any live run it re-formats and truncates all 55 labels each frame; and agent_list_projection is dropped by invalidate_agent_list() on every start_subagent (harness.rs:226), so a 40-way expansion fires 40 back-to-back full rebuilds. Neither is fatal at 55 rows. Both are the wrong shape if a graph reaches several hundred.

Tab filtering has one more wrinkle worth knowing: agent_rows_on filters after the tree is built (list.rs:258), and prefixes come from the unfiltered projection. On the Done tab a finished stage keeps its branch glyph while its still-running parent is filtered away. That exists today; a run makes it routine rather than rare.

FAILURE MODES

What this can get wrong

A run that never drains The engine only advances when a completion arrives. A stage dropped without a counter decrement — a spawn error that is not fed back as a failure, a map expanding to zero — leaves nodes pending with nothing in flight to wake anything. Assert the invariant on every completion: in-flight empty and ready empty with pending non-empty is a bug, not a wait. Back it with a run-level deadline composed the way execution_deadline already composes worker and configured deadlines (background.rs:143).
A global cancel_all wedges every live run cancel_all bumps generation and installs a fresh root token (manager.rs:329), so every in-flight completion becomes stale: is_current returns false and push drops it. The engine then never hears from its stages and hangs with nothing in flight to wake it. Whoever calls cancel_all must drop every live Dag in the same critical section — not cleanup, but the difference between a stopped run and a wedged one. Two existing callers already go through it: ManagerLifetime::drop at session teardown (manager.rs:91) and CompletionInbox::reset on /clear (completions.rs:139). Both must clear the run map.
Silent failure is invisible by construction The point of the design is that the parent does not read stage output. A stage returning confident garbage propagates unchallenged. The terminal RunOutcome must carry a per-stage status line, and a failed stage must surface as an error rather than an empty string folded into the next prompt.
A freshly generated graph is wrong in a fresh way each time A file gets reviewed once and is then correct forever. A graph composed per run can be subtly wrong every run — dependencies that force serialisation where none was needed, a map over something that was never a list, fan-out nobody sized. Validation catches the structural errors; the shape errors need feedback, so the terminal RunOutcome should report realised parallelism and per-stage timing, not just answers.
Expressiveness runs out needs and map cover fan-in and fan-out — not branches, not arbitrary control flow. A workflow that genuinely needs loops is a signal to revisit the model, not to embed an interpreter.

Decisions to make before P1

01 — extending a live run
Composing a graph per run covers "the shape depends on this job"; it does not cover "the shape depends on what stage 4 found", beyond what map expresses. An extend action adding stages to a live run is additive — the engine already inserts nodes mid-run for map — but it needs a rule for extending a stage that has already completed. Ship without it, design so it fits.
02 — strictness of schema
The parent writes it inline, so a real type language is clearly scope creep. string[] plus a named JSON shape probably suffices — but whatever it is must be checkable at submit, or template validation in P1 has nothing to check against.
03 — approval flow
Stages inherit host hooks through runtime::subagents::extensions, so a run can produce many approval prompts with no parent narrative explaining them. Batch per run, or have the submitted graph declare a permission scope the user approves once.
04 — the run-level spawn
Recommended in section 04 and assumed by sections 10 and 12, but it requires a no-slot admission variant in the manager. Confirm before P2, since the terminal-delivery path and the TUI grouping both depend on it.
