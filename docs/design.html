Scheduling semantics

Parallel by default.
Ordered by contract.

Each tool classifies each call. The dispatcher extracts all safe concurrency without allowing conflicting work to overlap.

Parallel

Independent calls fan out immediately. This is the default.

all lanes open

Keyed

Calls sharing one resource key serialize; unrelated keys continue.

same path, one chain

Multiple keys

A call touching several resources joins every conflicting chain.

rename: source + target

Serial

Exclusive work waits until every other call has cleared.

one call, full lock

Completion order is allowed to vary. Model-visible order is not. Every result keeps its call ID and returns in the original request order—even through cancellation or deadlines.

Extension lifecycle

Surround the loop.
Never replace it.

Extensions subscribe only to the events they use. Registration compiles those subscriptions into event-specific arrays, so an unused hook is one empty-slice check.

Precise seams,
not plugins everywhere.

Deterministic hooks transform state in call order. Live completion observation is the deliberate exception.

on_agent_start

Prepare transient run state.

before_model

Shape context before generation.

model_delta

Observe streaming text and reasoning without changing authority.

after_model

Meter usage and inspect the authoritative response.

before_tool

Allow, deny, validate, approve, or rewrite arguments before execution.

around_tool

Wrap the call with retry, timeout, tracing, or sandbox routing.

after_tool

Truncate, redact, or normalize the collected result.

tool_finished

Observe live completion from the executing task using identity and error status only.

tool_result

Audit the final, model-visible result.

on_error

Observe the terminal harness error path.

on_agent_end

Close out the run whether it answered or failed.

The product boundary

Own less.
Guarantee more.

Orca Harness is an execution primitive, not a distributed agent platform. The line is intentional.

The harness owns

One agent run

  • Agent configuration and context
  • Model invocation and streaming
  • Tool dispatch and concurrency
  • Cancellation, deadlines, and limits
  • Call/result identity and ordering
  • The extension lifecycle
The surrounding system owns

The fleet around it

  • Distributed scheduling
  • Durable sessions and persistence
  • MicroVM and sandbox lifecycle
  • Networking and tenancy
  • Fleet management and scaling
  • Control-plane APIs

Context is not durable memory. Durable sessions and memory can be provided by extensions or by the host; they do not become kernel concerns.
